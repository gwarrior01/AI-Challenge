# Ассистент разработчика: `/help`

`/help <вопрос>` — вопрос о самом проекте: как он устроен, где что лежит, как запустить, какие у него API и схемы данных, что сейчас в репозитории. Отвечает ассистент, который знает документацию проекта (RAG) и видит репозиторий через MCP-сервер git. Код — `core/src/devhelp.rs` (интерфейсы только вызывают `devhelp::ask`).

```text
/help <вопрос>
  1. MCP git · git_branch   — текущая ветка, последний коммит, число изменённых файлов (вызывает код, всегда)
  2. индекс документации    — README.md + docs/ сверяются с файлами; изменившиеся переиндексируются
  3. поиск (RAG)            — вопрос + перевод терминов → structure-фрагменты → порог 0.5 → эвристический реранкинг → 6 фрагментов
  4. модель                 — фрагменты [n] + контекст git + инструменты git: list_files, git_status, git_diff, git_log
  5. ответ                  — с блоком «Источники»: фрагменты, на которые модель сослалась [n] (не сослалась ни на один — все, что она получила), и вызванные инструменты
```

## Где набирать

| Интерфейс | Как |
|---|---|
| TUI | `/help <вопрос>` в поле ввода прямого чата или чата агента. Над ответом — строка **Проект** (git, индекс, найденные фрагменты) и строки **Тул** с вызовами git |
| Веб | `/help <вопрос>` в поле «Чат» или в чате агента. Над ответом — карточка с контекстом, в чате агента ещё карточка RAG и раскрывающиеся вызовы инструментов. API: `POST /api/help {"question": "…"}` |
| CLI | `llm-cli help <вопрос>`, или `/help <вопрос>` в REPL и в `agent start` |

`/help` без вопроса — краткий обзор проекта. Обмен `/help` не попадает ни в память прямого чата, ни в историю агента: это справка, а не реплика диалога.

## Документация: свой индекс

- Корпус — `README.md` и всё в `docs/` (`.md`, `.txt`, `.rs`, `.pdf`); переопределяется `DEVHELP_DOCS` (через запятую). Папка `docs/` в корпусе всегда.
- Индекс — `rag/project.db` (`DEVHELP_DB`), отдельно от общего индекса агентов `rag/index.db`: там загруженные пользователем документы, и они не должны смешиваться со справкой о проекте, а полная индексация общего корпуса не должна снимать README с поиска.
- Стратегия нарезки — `structure`: раздел Markdown по заголовкам целиком, с путём разделов (`MCP › Own MCP server: git`).
- Перед каждым вопросом файлы сверяются по SHA-256: изменился — новая версия и эмбеддинги только изменившихся чанков; файл удалён — версия снимается с поиска. Отдельно переиндексировать не нужно: поправили `docs/api.md` — следующий `/help` уже знает новое. Строка `docs:` над ответом говорит, что переиндексировано.
- Сменилась модель эмбеддингов — индекс документации очищается и собирается заново сам (он целиком выводится из файлов).
- Нужна `LLM_EMBEDDING_MODEL` (как для RAG агентов). Без неё ассистент отвечает только по контексту git, а строка RAG над ответом говорит почему.

## Репозиторий: MCP-сервер git

`mcp/git-mcp` — свой MCP-сервер, только чтение. В `mcp.example.json` он под именем `git` (`DEVHELP_GIT_SERVER`) как stdio-сервер: `cargo run -q -p git-mcp` — клиент запускает его сам, сервер работает с репозиторием рабочей директории (`GIT_MCP_REPO`).

| Инструмент | Когда нужен |
|---|---|
| `git_branch` | Текущая ветка, HEAD, последний коммит, отставание от upstream, локальные ветки. Код вызывает его сам перед каждым вопросом |
| `git_status` | Что изменено и не закоммичено |
| `list_files` | Какие файлы есть: `depth=1`/`2` — обзор структуры с числом файлов в каталогах, `pattern="*.rs"` — поиск по имени, `path` — один каталог |
| `git_diff` | Сами изменения: незакоммиченные, `staged`, или `base="main"` — всё сделанное в ветке; `stat_only` — только файлы и строки |
| `git_log` | История всего репозитория или одного пути |

Ветку код запрашивает сам, а не оставляет модели: она нужна почти любому ответу, и решение «звать ли инструмент» не должно зависеть от модели. Остальные инструменты модель зовёт, когда вопрос про файлы, изменения или историю. Защита: git запускается без оболочки, ветка/коммит от модели проверяются (не начинаются с `-`, без `..`), пути — внутри репозитория, перед путями `--`.

Сервер git не подключён (нет в `mcp.json`, выключен, не собрался) — ответ всё равно будет, по документации; строка `git:` над ответом говорит, что не так. Включённый, но ещё не подключённый сервер `/help` подключает сам (или ждёт до 30 с, пока идёт подключение при старте интерфейса).

## Примеры вопросов

- `/help` — обзор проекта.
- `/help где лежит код RAG и из каких модулей он состоит?`
- `/help какие таблицы в agents.db и что в shared_tasks?`
- `/help какой эндпоинт веба включает RAG у агента?`
- `/help на какой я ветке и что изменено?` — git_branch + git_status.
- `/help что сделано в этой ветке относительно main?` — git_diff с `base="main"`.
- `/help какие MCP-серверы есть в репозитории и как добавить свой?`
- `/help покажи структуру каталога mcp` — list_files с `path="mcp"`, `depth=2`.

## Настройки

| Переменная | По умолчанию | Что |
|---|---|---|
| `ASSISTANT_MCP_CONFIG` | `assistant/mcp.json` | Конфигурация MCP ассистента (свой сервер git) |
| `ASSISTANT_GIT_SERVER` | `git` | Имя сервера git в конфигурации MCP |
| `ASSISTANT_DOCS` | `README.md,docs` | Корпус документации |
| `ASSISTANT_DOCS_DB` | `rag/project.db` | Индекс документации |
| `ASSISTANT_CODE` | `core/src,cli/src,tui/src,web/src,assistant/src,gateway/src,mcp` | Корпус кода |
| `ASSISTANT_CODE_DB` | `rag/code.db` | Индекс кода |
| `ASSISTANT_REVIEW_BASE` | `main` | Базовая ветка ревью по умолчанию |
| `ASSISTANT_REVIEW_MAX_CHARS` | `48000` | Бюджет символов диффа на один запрос ревью |
| `ASSISTANT_REVIEW_REASONING` | `off` | Рассуждения модели при ревью (`on`/`1`/`true` — включить) |
| `ASSISTANT_LLM_TIMEOUT` | `180` | Сколько секунд ждать ответ модели на запрос |
| `ASSISTANT_DUMP_DIR` | — | Отладка: каждый запрос к модели пишется туда JSON-файлом |
| `GIT_MCP_REPO` | рабочая директория | Репозиторий для `git-mcp` |
| `GIT_MCP_ADDR` | `127.0.0.1:8094` | Адрес `git-mcp` в режиме `--http` |
| `LLM_API_URL` | — | Адрес LLM API (обязательна) |
| `LLM_API_KEY` | — | Ключ API (обязателен) |
| `LLM_MODEL` | `gpt-4o-mini` | Модель для чата |
| `LLM_CONTEXT_WINDOW` | — | Размер контекстного окна в токенах (иначе 262000) |
| `LLM_EMBEDDING_MODEL` | — | Модель эмбеддингов (обязательна для поиска по документации и коду) |
| `LLM_EMBEDDING_API_URL` | как `LLM_API_URL` | Адрес API эмбеддингов, если не тот же, что у чата |
| `LLM_EMBEDDING_API_KEY` | как `LLM_API_KEY` | Ключ API эмбеддингов |
| `LLM_EMBEDDING_BATCH` | `32` | Сколько текстов в одном запросе `/embeddings` |
| `LLM_EMBEDDING_DOC_PREFIX` | — | Префикс документов для моделей, которые его ждут |
| `LLM_EMBEDDING_QUERY_PREFIX` | — | Префикс запросов для моделей, которые его ждут |
