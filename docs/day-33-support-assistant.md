# День 33: ассистент поддержки пользователей

`support-assistant` — отдельный мини-сервис поддержки продукта CloudDesk (демо). Он работает в двух режимах: как консультант по продукту (что умеет, тарифы, как что-то сделать) и как поддержка, разбирающая конкретный тикет с учётом данных клиента из CRM:

- **RAG** — документация и FAQ продукта из `support/knowledge/*.md` в собственном индексе `rag/support.db`:
  - `product.md` — что это, из чего состоит, платформы, как начать;
  - `plans.md` — тарифы, цены, пробный период, смена и отмена;
  - `team.md` — участники и роли;
  - `projects.md` — проекты, задачи, файлы, уведомления;
  - `reports.md` — отчёты и экспорт;
  - `integrations.md` — интеграции и API;
  - `security.md` — безопасность и данные;
  - `authentication.md` — вход и 2FA;
  - `billing.md` — оплата;
  - `faq.md` — частые вопросы;
- **MCP** — CRM: свой сервер `mcp/support-mcp` только для чтения, пользователи и тикеты из `support/data/users.json` и `tickets.json`;
- **сессия** — сервис помнит тикет и последние обмены, поэтому уточняющий вопрос без номера тикета понимается в контексте.

## Как строится ответ

```text
вопрос (+ ticket_id, + session_id)
  → номер тикета: назван в вопросе › передан в ticket_id (API, --ticket) › тикет сессии
  → MCP support · get_ticket      — кодом, всегда: тикет + профиль клиента
    (тикета нет: USR-… в вопросе или клиент сессии → get_user)
  → RAG: поиск по самому вопросу; если есть тикет — ещё по вопросу + теме тикета + коду ошибки → фрагменты [n]
  → модель: данные CRM, фрагменты, история сессии;
    при нужде сама вызывает search_knowledge и MCP get_ticket / get_user / list_user_tickets
  → ответ: о продукте — как консультант, без номера тикета;
            о проблеме — причина → что сделать → когда эскалировать; «Источники» — только процитированные [n]
```

Тикет запрашивает код, а не модель. Поэтому ответ с учётом тикета не зависит от того, догадается ли модель вызвать инструмент. Если тикет не найден или CRM недоступна, модель получает об этом пометку и не придумывает содержимое тикета.

## Запуск

Нужны чат-модель и модель эмбеддингов (`LLM_*`, `LLM_EMBEDDING_MODEL`, см. корневой README). CRM отдельно поднимать не нужно: сервис сам запускает `support-mcp` дочерним процессом через stdio (`support/mcp.json`). База знаний индексируется при старте и сверяется с файлами (SHA-256) перед каждым ответом, поэтому правка статьи видна без перезапуска.

```bash
cargo run -p support-assistant            # http://127.0.0.1:8096
```

Страница — обычный чат: спрашивайте о продукте или о своём обращении, номер тикета пишется прямо в вопросе («Тикет TCK-1001. …») и дальше запоминается в разговоре. Под ответом — источники из базы знаний, на которые он ссылается. Кнопка «Новый разговор» сбрасывает сессию.

Без интерфейса:

```bash
cargo run -p support-assistant -- tickets
cargo run -p support-assistant -- ask "Тикет TCK-1001. Почему не работает авторизация?"
cargo run -p support-assistant -- ask --ticket TCK-1002 "Почему пропал экспорт?"
```

### API

| Метод | Путь | Что делает |
|---|---|---|
| `GET` | `/` | страница чата |
| `POST` | `/api/ask` | `{question, session_id?, ticket_id?}` → `{session_id, answer, ticket, customer, crm_note, sources, cited, tool_calls, context_lines, usage, …}` |
| `POST` | `/api/reset` | `{session_id}` — забыть разговор |

### Настройки

| Переменная | По умолчанию |
|---|---|
| `SUPPORT_ADDR` | `127.0.0.1:8096` |
| `SUPPORT_KNOWLEDGE` | `support/knowledge` (пути через запятую) |
| `SUPPORT_RAG_DB` | `rag/support.db` |
| `SUPPORT_MCP_CONFIG` | `support/mcp.json` |
| `SUPPORT_CRM_SERVER` | `support` |
| `SUPPORT_LLM_TIMEOUT` | `120` (секунды на запрос к модели) |
| `SUPPORT_DATA_DIR` (для `support-mcp`) | `support/data` |

`support-mcp --http` поднимает CRM как Streamable HTTP на `127.0.0.1:8095/mcp` (`SUPPORT_MCP_ADDR`). Порт 8094 занят `git-mcp --http`.

## Демо-запросы

Вопросы о продукте, без тикета:

> Что такое CloudDesk и на каких устройствах он работает?
> Чем Pro отличается от Business и сколько стоит?
> Как пригласить коллегу в пространство?
> Есть ли у вас интеграция с Jira?

Ответы строятся по статьям базы знаний со ссылками [n], номер тикета ассистент не просит. Про Jira он должен честно сказать, что готовой интеграции нет, и предложить API, а не выдумывать её.

Если в разговоре уже есть тикет, вопрос о продукте ищется отдельно от темы тикета. Поэтому «Как пригласить коллегу?» после TCK-1001 находит статью про участников, а не статью про блокировку входа.

Разбор тикета:

> Тикет TCK-1001. Почему не работает авторизация и что мне делать?

Будут вызовы `MCP support · get_ticket` и `RAG search_knowledge`. Ответ соединяет факты тикета (`AUTH-LOCKED`, 7 неудачных попыток, код 2FA запрашивали несколько раз) с инструкцией из `authentication.md`: блокировка на 15 минут, новые попытки её продлевают, действует только последний код.

Продолжение в той же сессии, без номера тикета:

> А если после 15 минут код всё равно не придёт?

Тикет берётся из сессии. Ответ ведёт к форме восстановления доступа и предупреждает, что поддержка не отключает 2FA в чате.

Ответ зависит от данных клиента:

> Тикет TCK-1002. Почему пропал экспорт отчётов?

У Ивана оплачен тариф Pro, но аккаунт в статусе `payment_hold`: последний платёж отклонён. Ответ должен объяснить, что платные функции на удержании отключены, и предложить обновить способ оплаты. Общий ответ «экспорт есть только на Pro» здесь неверен.

Негативная проверка:

> Посмотри тикет TCK-9999.

`get_ticket` вернёт ошибку. Ассистент должен сказать, что тикет не найден, и попросить номер, ничего не придумывая. Блока «Источники» в таком ответе нет.

## Альтернатива: named agent

Тот же сценарий можно собрать без сервиса, из готовых агентов, RAG и MCP: в `mcp.json` должна быть секция `support` из `mcp.example.json`.

```bash
# Свой индекс, чтобы не трогать основной rag/index.db агентов
export RAG_CORPUS=support/knowledge RAG_DB_PATH=rag/support.db
cargo run -p llm-cli -- rag index structure
cargo run -p llm-cli -- agent add Поддержка --system "$(cat support/agent-prompt.md)" --context-strategy summary
cargo run -p llm-cli -- agent rag Поддержка on structure k=4 min=0.45 rerank=heuristic
```

Дальше в том же терминале, с теми же переменными, откройте агента «Поддержка» в TUI (`cargo run -p llm-tui`; RAG — Ctrl+R, вызовы MCP видны строками «Тул:») или в веб-интерфейсе (`cargo run -p llm-web`). Отличие от сервиса: тикет здесь подтягивает модель по промпту, а не код, и слабая модель может этот шаг пропустить.

## Проверка кода

```bash
cargo fmt -p support-assistant -p support-mcp -- --check
cargo clippy -p support-assistant -p support-mcp
cargo test -p support-assistant -p support-mcp
```

Тесты `support-mcp` проверяют загрузку демо-CRM, связи тикетов с клиентами, сортировку и фильтр списка тикетов, а также отказ при дублирующихся или неизвестных идентификаторах. Тесты `support-assistant` проверяют:

- поиск номеров тикетов и клиентов в тексте;
- поисковый запрос с темой тикета и кодом ошибки;
- содержимое промпта (данные CRM, фрагменты, «тикет не найден»);
- общую нумерацию фрагментов и источники только по ссылкам [n];
- объяснение, почему CRM недоступна.

## План видео

1. Показать базу знаний (`support/knowledge`) и JSON CRM (`support/data`).
2. Запустить `cargo run -p support-assistant` и показать в логе индексацию базы знаний и подключение CRM по MCP.
3. Открыть страницу и задать пару вопросов о продукте без тикета (тарифы, интеграции, Jira): ответы по документации, номер тикета не нужен.
4. Спросить «Тикет TCK-1001. Почему не работает авторизация?», показать источники под ответом. Вызовы `get_ticket` и `search_knowledge` видно в `support-assistant ask …` в терминале.
5. Спросить «А если после 15 минут код всё равно не придёт?» без номера: работает контекст сессии.
6. Посреди разговора спросить о продукте («Как пригласить коллегу?»): ответ по статье про участников, тикет не мешает.
7. Задать вопрос по TCK-1002: ответ зависит от `payment_hold`, а не только от тарифа.
8. Спросить про TCK-9999: тикет не найден, ассистент ничего не выдумывает.
