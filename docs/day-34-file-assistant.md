# День 34: ассистент для работы с файлами проекта

`file-assistant` — ассистент, который сам работает с файлами, а не только отвечает текстом. Ему ставят цель словами («найди все места, где используется `McpManager`», «обнови таблицу настроек по коду», «сгенерируй CHANGELOG»). Какие файлы искать, читать и править, он решает сам:

- **MCP `fs`** — свой сервер `mcp/fs-mcp`: список файлов, поиск по содержимому, чтение, создание и правка файлов;
- **MCP `git`** — уже знакомый `mcp/git-mcp`, только чтение: история и изменения (для changelog, ADR, «что сделано в ветке»);
- **изменения** не пишутся на диск сами. Они копятся как ожидающие и показываются диффом, а записывает их пользователь (`/apply`, `--apply`);
- **запуск** сохраняется в `files/runs/<id>/` с отчётом, патчем и журналом вызовов, поэтому результат можно проверить и повторить.

## Как выполняется задача

```text
цель словами (или сценарий из files/scenarios)
  → git_branch (кодом, если git подключён) + ожидающие изменения от прошлых задач (кодом)
  → модель, до FILES_MAX_ROUNDS кругов, сама выбирает инструменты:
      fs  · list_files, search, read_file           — разведка и чтение
      fs  · edit_file, write_file, discard_changes  — правки: в оверлей, не на диск
      fs  · pending_changes                         — проверить свой дифф
      git · git_log, git_diff, git_status           — история и изменения
  → отчёт модели (Markdown: итог, находки `путь:строка`, изменения)
  → дифф ожидающих изменений (кодом) → files/runs/<id>/
  → пользователь: /apply — записать · /discard — отказаться · или позже git apply …/changes.patch
```

Системный промпт задаёт порядок работы: сначала разведка, потом чтение, и только потом выводы и правки. Опираться можно только на прочитанное. Если цель — «найди» или «проверь», файлы не меняются. Правки минимальные, в стиле соседнего текста, и в конце модель сама проверяет дифф через `pending_changes`. В промпт также подмешиваются инварианты проекта из `invariants/`, как у агентов.

Защита цикла (появилась после прогонов на реальной модели: в одном из них модель 13 раз подряд читала `README.md` с первой строки и так и не создала файл):

- **Повторы.** Тот же вызов с теми же доводами (порядок ключей неважен), если файлы с тех пор не менялись, не выполняется. Модель получает «уже было на шаге N, результат выше». После `edit_file`, `write_file` и `discard_changes` счёт начинается заново.
- **Бюджет шагов.** Модель знает лимит с самого начала. За 5 шагов до конца она получает указание переходить к правкам и отчёту, а на последнем шаге инструменты ей уже не выдаются.
- **Сбой модели.** Таймаут или ошибка провайдера: запрос повторяется один раз. Если и повтор не удался после хотя бы одного шага, задача завершается частичным результатом: замечание, сохранённый запуск, накопленные правки.
- **Только выданные инструменты.** Инструмент не из списка (в том числе `apply_changes`) не вызывается, даже если модель его назовёт.

## Где набирать

| Интерфейс | Как |
|---|---|
| TUI (основной) | `cargo run -p file-assistant`. Цель — просто текстом. В шапке видны серверы `fs`/`git`, ветка и **сколько изменений ждёт записи**. Вызовы инструментов появляются в ленте плашками « MCP » по мере того, как модель их делает. После задачи в ленте отчёт и цветной дифф |
| CLI | `file-assistant run <цель…>` или `run --scenario <имя>`: отчёт и дифф — в stdout, вызовы — в stderr. `--apply` записывает изменения на диск, `--out <каталог>` задаёт, куда сохранить запуск, `--quiet` отключает вывод вызовов |

### Команды TUI

| Команда | Что делает |
|---|---|
| `<цель>`, `/task <цель>` | Задача. Ассистент сам находит, читает и правит файлы |
| `/scenario [имя]` | Готовая цель из `files/scenarios`; без имени — список |
| `/diff` | Ожидающие изменения: файлы, `+/−` строк, дифф |
| `/apply [путь…]` | Записать на диск все изменения или только эти файлы/каталоги. Отмечается в `run.json` последнего запуска |
| `/discard [путь…]` | Отказаться от изменений |
| `/files [путь]` | Структура проекта или каталога |
| `/calls [off\|brief\|debug]` | Как показывать вызовы MCP: скрыть, кратко (`сервер › инструмент ✓`, без доводов) или для отладки (доводы целиком и результат). Без аргумента — следующий режим, то же, что **Ctrl+O** |
| `/clear`, `/?`, `/quit` | Очистить ленту, справка, выход |

Ленту прокручивает колесо мыши (и PgUp/PgDn). Режим показа вызовов меняется сразу для всей ленты, в том числе для уже показанных вызовов. Текущий режим виден в заголовке ленты (`tools calling: кратко`), начальный задаёт `TUI_CALLS`. Чтобы выделить текст мышью, держите Option (iTerm2) или Fn (Terminal.app). То же в `code-assistant` и в основном `llm-tui`.

Ожидающие изменения переживают задачу: следующая цель («а теперь добавь туда ещё…») видит их, и модели сообщают, что они уже есть. Живут они, пока запущен ассистент. Вышли без `/apply` — правки останутся только в `changes.patch` запуска.

## Сценарии

Готовые цели лежат в `files/scenarios/*.md`: первая строка — название, дальше — цель так, как её сформулировал бы человек. Список выводит `file-assistant scenarios`.

| Сценарий | Что делает | Файлы |
|---|---|---|
| `usages` | Все места, где используется `McpManager`: где создают, подключают, вызывают инструменты, с группировкой по крейтам и ссылками `путь:строка` | только чтение, десятки файлов |
| `docs-sync` | Сверяет таблицу настроек в `docs/developer-assistant.md` с переменными, которые реально читает `assistant/src`, и обновляет таблицу | читает код и документ, правит документ |
| `changelog` | Генерирует `CHANGELOG.md` по истории git (дни `day-N`) и документации в `docs/` | git + чтение, новый файл |
| `invariants` | Проверяет проект на инварианты из `invariants/`: вердикт по каждому, нарушения с `путь:строка` | только чтение |

Сценарии покрывают четыре из пяти примеров задания: поиск использований, обновление документации по коду, генерацию нового файла и проверку на инварианты. Пятый пример, diff и список изменений, есть у каждой задачи с правками.

## Повторяемость

Каждый запуск сохраняется в `files/runs/<UTC-время>-<сценарий|цель>/` (`FILES_RUNS_DIR`, каталог в `.gitignore`). Хранятся только последние `FILES_RUNS_KEEP` запусков (по умолчанию 50): после сохранения нового самые старые удаляются:

| Файл | Что внутри |
|---|---|
| `goal.md` | Цель и сценарий |
| `report.md` | Отчёт модели и замечания (git недоступен, упёрлись в предел шагов) |
| `changes.patch` | Дифф в формате git. Применяется отдельно: `git apply files/runs/<id>/changes.patch` |
| `tools.json` | Все вызовы инструментов: доводы и результаты |
| `run.json` | Модель, температура, шаги, токены, файлы, которые модель читала и меняла, изменения; после `/apply` — что записано и какие были конфликты |

Температура по умолчанию — `0`, поэтому повторный запуск того же сценария на той же модели и тех же файлах даёт тот же результат или очень близкий к нему.

## MCP-сервер `fs` (`mcp/fs-mcp`)

По умолчанию работает через stdio: ассистент сам запускает `cargo run -q -p fs-mcp` (см. `files/mcp.json`). Корень — рабочая директория (`FS_MCP_ROOT`). С `--http` сервер работает по Streamable HTTP на `127.0.0.1:8097/mcp` (`FS_MCP_ADDR`).

| Инструмент | Аргументы | Возвращает |
|---|---|---|
| `list_files` | `path?`, `pattern?` (`*.rs`, `*.md,*.toml`, `docs/**/*.md`), `depth?`, `limit?` (300) | `total`, `truncated`, `files[]` — или с `depth` `tree[]` {path, files} |
| `read_file` | `path`, `start_line?`, `max_lines?` (400) | `path`, `start_line`, `end_line`, `total_lines`, `text`, `truncated`, `pending` |
| `search` | `query`, `regex?`, `case_sensitive?`, `path?`, `pattern?`, `context?` (0–5), `max_results?` (50) | `total_matches`, `files[]` {path, matches} — полностью, `matches[]` {path, line, text, before, after}, `truncated`, `files_scanned` |
| `write_file` | `path`, `content` | `path`, `created`, `lines`, `added`, `deleted`, `diff` |
| `edit_file` | `path`, `old_text`, `new_text`, `replace_all?` | то же + `replacements` |
| `pending_changes` | — | `files[]` {path, status: created/modified, added, deleted}, `added`, `deleted`, `patch` |
| `discard_changes` | `paths?` | `discarded[]` |
| `apply_changes` | `paths?` | `written[]`, `conflicts[]` {path, reason}. **Модели не выдаётся**, его вызывает код ассистента |

**Оверлей.** `write_file` и `edit_file` кладут новое содержимое в память сервера вместе с тем, что было на диске при первой правке. `read_file`, `search` и `list_files` идут через оверлей, поэтому модель видит свои правки. Если правка вернула файл к содержимому на диске, изменение исчезает. `apply_changes` записывает файл, только если на диске он с тех пор не изменился. Если изменился, это конфликт: файл не трогается, а изменение остаётся в оверлее, от него можно отказаться. Удаления нет.

**`edit_file`.** Фрагмент `old_text` должен совпадать с файлом символ в символ и встречаться ровно один раз. Иначе сервер возвращает ошибку с подсказкой: «нет такого фрагмента — перечитай место» или «встречается 3 раза (строки 1, 2, 3) — добавь соседние строки или `replace_all`».

**Песочница.** Пути считаются от корня. Запрещены `..`, абсолютные пути вне проекта и симлинки наружу. Обход учитывает `.gitignore`. Для чтения и для записи всегда закрыты `.git/`, `target/`, `node_modules/`, `.env` и `.env.*` (кроме `.env.example`), а также `*.db*`, `*.sqlite`, `*.pem`, `*.key` (инвариант `secrets`). Пределы: файл до 1 МБ, двоичные файлы не читаются, в оверлее не больше 60 файлов.

## Устройство

| Где | Что |
|---|---|
| `mcp/fs-mcp/src/workspace.rs` | Песочница путей, обход, поиск, оверлей, дифф (`similar`), запись с проверкой конфликтов |
| `mcp/fs-mcp/src/main.rs` | Инструменты MCP (rmcp), stdio / Streamable HTTP |
| `files/assistant/src/task.rs` | Задача: промпт, цикл «модель → инструменты», отчёт |
| `files/assistant/src/session.rs` | Модель и MCP. Какие инструменты видит модель (без `apply_changes`; из git — только история), вызовы кодом: дифф, запись, отказ |
| `files/assistant/src/runs.rs` | Сохранение запуска, обрезка старых (`FILES_RUNS_KEEP`) |
| `files/assistant/src/scenarios.rs` | Сценарии из `files/scenarios` |
| `files/assistant/src/tui.rs`, `main.rs` | TUI и CLI |
| `assistant-tui/` | Лента, строка ввода, Markdown — общие с `code-assistant` |

## Настройки

| Переменная | По умолчанию | Что |
|---|---|---|
| `LLM_API_URL`, `LLM_API_KEY`, `LLM_MODEL` | — | Модель (как у остального проекта). Нужна модель, которая умеет вызывать инструменты |
| `FILES_MCP_CONFIG` | `files/mcp.json` | Конфигурация MCP ассистента |
| `FILES_FS_SERVER` / `FILES_GIT_SERVER` | `fs` / `git` | Имена серверов в ней |
| `FILES_MAX_ROUNDS` | `30` | Сколько кругов «модель → инструменты» на задачу |
| `FILES_TEMPERATURE` | `0` | Температура |
| `FILES_TOOL_RESULT_CHARS` | `24000` | Длиннее этого результат инструмента обрезается для модели (с подсказкой сузить запрос) |
| `FILES_LLM_TIMEOUT` | `180` | Сколько секунд ждать ответа модели на один запрос |
| `FILES_RUNS_DIR` | `files/runs` | Куда сохранять запуски |
| `FILES_RUNS_KEEP` | `50` | Сколько последних запусков хранить: после сохранения нового самые старые удаляются |
| `FILES_RUNS_KEEP` | `50` | Сколько последних запусков хранить; старше удаляются при сохранении нового |
| `FILES_SCENARIOS_DIR` | `files/scenarios` | Где лежат сценарии |
| `TUI_CALLS` | `brief` | Начальный режим показа вызовов MCP во всех TUI: `off`, `brief`, `debug` |
| `FS_MCP_ROOT` / `FS_MCP_ADDR` | рабочая директория / `127.0.0.1:8097` | Корень и адрес (`--http`) сервера `fs` |

## Проверка

```bash
cargo test -p fs-mcp                           # песочница, поиск, оверлей, конфликты, git apply патча
cargo test -p file-assistant                   # промпт, аргументы, сохранение запуска, сценарии
cargo test -p file-assistant -- --ignored      # живой fs-mcp по stdio через McpManager
cargo run -p file-assistant -- run --scenario usages
cargo run -p file-assistant -- run --scenario docs-sync      # дифф, без записи
git apply --check files/runs/<id>/changes.patch
```
