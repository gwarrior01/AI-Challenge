# Локальная LLM как приватный сервис — отчёт

Замеры 2026-10-11 на VPS `91.188.212.172`, запросы шли по сети с рабочей машины.

## Сервер

| | |
|---|---|
| ОС | Ubuntu 24.04, KVM |
| CPU | 1 vCPU Intel Xeon Sapphire Rapids (AVX2, AVX-512, VNNI) |
| RAM | 1,9 ГБ + swap 4 ГБ (добавлен `setup.sh`) |
| GPU | нет |

## Схема

```
клиент (llm-cli / llm-web / llm-tui, curl, OpenAI SDK, страница чата на GET /)
   │ HTTP :8080, Authorization: Bearer <ключ пользователя>
   ▼
llm-gateway  — ключи, rpm на пользователя, лимит контекста, очередь к слотам, /stats
   │ 127.0.0.1:8081 (ufw: снаружи открыты только 22 и 8080)
   ▼
llama-server (llama.cpp b11552, CPU) — 3 слота × 2048 токенов, continuous batching
```

## Выбор модели

Обе модели Qwen2.5-Instruct в Q4_K_M, ответ до 64 токенов, замер на самом сервере.

| Модель | Файл | RAM занято | 1 запрос: промпт / генерация | 3 параллельно: генерация на каждый | 3 запроса за |
|---|---|---|---|---|---|
| **qwen2.5-1.5b-instruct** | 1,1 ГБ | ~1,4 ГБ | 57 / 8,6 ток/с | 4,1–4,5 ток/с | 15,9 с |
| qwen2.5-0.5b-instruct | 469 МБ | ~0,6 ГБ | 86 / 21,0 ток/с | 11–13 ток/с | 7,1 с |

Выбрана **1.5B**: на трёх пользователях она даёт ~4 ток/с каждому, а 0.5B заметно хуже
по-русски («языковые моделлы», «Королевская Контрольная кофейница»). 0.5B лежит на сервере
запасной — переключение одной строкой `MODEL=` в `/etc/llm/llama.env`.

Грабли: с `--load-mode mmap+mlock` модель 1.5B не влезала. CPU-сборка переупаковывает веса
под AVX-512 (repack) в свою копию, а mlock держал в RAM ещё и исходный mmap — две копии модели,
сервер уходил в swap (83 % iowait, первый ответ не пришёл и за 5 минут). Без mlock — 1,4 ГБ
и swap не растёт.

## Нагрузка по сети: 3 пользователя одновременно

`llm-gateway loadtest --url http://91.188.212.172:8080 --keys k1,k2,k3 --requests 3 --max-tokens 64` —
у каждого пользователя свой ключ, все трое шлют серии запросов одновременно.

| Пользователь | Запросов | Успешно | Средняя задержка | Токенов ответа |
|---|---|---|---|---|
| 1 | 3 | 3 | 15,0 с | 190 |
| 2 | 3 | 3 | 15,1 с | 192 |
| 3 | 3 | 3 | 15,0 с | 192 |

- 9 запросов, успешно 9, ошибок 0;
- задержка p50 15,0 с, p95 16,3 с — пользователи обслуживаются поровну;
- общая скорость генерации 12,7 ток/с (574 токена за 45,3 с) — больше, чем 8,6 ток/с одного
  запроса: continuous batching считает три слота за один проход по весам;
- память и swap после серии не выросли.

## Ограничения

| Проверка | Ожидание | Результат |
|---|---|---|
| Неверный ключ | 401 | 401 `invalid_api_key` |
| Промпт на ~5000 слов | 400 `context_length_exceeded` | 400 `context_length_exceeded` |
| Частые запросы, лимит 20/мин | 429 + `Retry-After` | 429 `rate_limit_exceeded` на 17-м (ещё 4 запроса этого ключа уже были в окне) |
| `max_tokens: 100000` | урезается до 512 | проверено юнит-тестом |
| Порт llama-server 8081 снаружи | закрыт | закрыт (ufw) |

Лимиты (`/etc/llm/gateway.toml`):

- **контекст** — промпт (через шаблон чата и токенизатор самой модели) + `max_tokens` ≤ 2048
  (CTX_SIZE 6144 / 3 слота);
- **длина ответа** — `max_tokens` по умолчанию 256, потолок 512;
- **rpm** — 20 запросов в минуту на ключ (у alice 30), скользящее окно;
- **параллельность** — 1 запрос пользователя одновременно (его следующий ждёт), 3 в модели,
  до 6 в очереди, ждать не дольше 120 с — иначе 503 `server_busy`.

Переполнение общей очереди по сети не воспроизвести с тремя ключами: при одном запросе на
пользователя в модель одновременно идут максимум трое, лишние запросы ждут у своего ключа.
Очередь, её переполнение и таймаут проверены юнит-тестами (`limits.rs`).

## Подключение нашего приложения

```bash
LLM_API_URL=http://91.188.212.172:8080/v1 LLM_API_KEY=<ключ> LLM_MODEL=qwen2.5-1.5b-instruct \
LLM_CONTEXT_WINDOW=2048 llm-cli "Сколько будет 2+2? Ответь коротко."
# 2+2=4
# [токены: запрос 45 + ответ 6 = всего 51]
```
